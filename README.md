# mark-support-mvp

中小企業向けPマーク取得・運用支援ツールのMVP

最初の業務機能として、教育管理MVPを実装済みです。ブラウザから
「対象者確認 → 不足の把握 → 不足解消操作 → 再評価 → 適合」という
一連の流れをデモできます。

## 構成

* Python 3.12
* FastAPI
* Uvicorn
* Pydantic
* pytest
* GitHub Codespaces / devcontainer

## 起動

```bash
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

起動後、ブラウザで `http://localhost:8000/` にアクセスするとトップページが、
`http://localhost:8000/health` にアクセスするとヘルスチェック用のJSONが表示されます。
`http://localhost:8000/education` にアクセスすると教育管理デモ画面が、
`http://localhost:8000/vendors` にアクセスすると委託先管理デモ画面が、
`http://localhost:8000/access-control` にアクセスするとアクセス権限管理デモ画面が、
`http://localhost:8000/paper` にアクセスすると紙媒体管理デモ画面が表示されます
（トップページからもリンクしています）。`http://localhost:8000/documents` に
アクセスすると、文書一覧（個人情報管理台帳・教育手順・委託先管理手順・
アクセス権限管理手順・紙媒体管理手順）が表示されます。

## テスト

```bash
python3 -m pytest -q
```

## 教育管理MVP デモ

教育管理を題材に、「事実データ → 業務ルール → 評価結果」を分離した構造を
ブラウザ上で確認できます。判定ロジック（`app/education.py` の
`evaluate_training()`）はHTML/APIから独立しており、画面側で独自の適合判定は
行いません。

### デモ企業

`株式会社サンプル`（従業者50名）の固定データを、サーバー起動時にメモリ上へ
構築します。

* 経営者1名、個人情報保護管理者1名、Pマーク担当者1名、一般従業員47名（全員active）
* 教育対象者50名のうち、初期状態では48名が受講済み・2名が未受講
* 受講済み48名のうち3名は理解度確認が未登録
* 教材証跡は未登録、実施結果は未承認

### デモシナリオ

1. `/education` を開くと、会社情報・教育管理策・規程条項プレビュー・
   年間教育計画・教育実績（未受講/要確認者を優先表示）・整合性チェック結果
   が表示されます。
2. 初期状態は **要対応**（`EDU-003` 未受講者2名 / `EDU-006` 理解度確認不足
   3名 / `EDU-008` 教材証跡未登録 / `EDU-009` 未承認）です。
3. 画面下部のボタンで、未受講者の受講済み化・理解度確認登録（`pass`）・
   教材証跡登録・承認、をそれぞれ操作できます。
4. 各操作のたびに `evaluate_training()` が再実行され、結果が画面に反映され
   ます。すべて解消すると **適合** になります。
5. 「デモを初期状態に戻す」ボタンで、いつでも初期状態（要対応）に戻せます。

### データ保存について

DBは使用していません。デモ状態はプロセス内メモリのみで保持しており、
サーバーを再起動すると初期状態（要対応）に戻ります。

## Codespaces

GitHub Codespacesでリポジトリを開くと、`.devcontainer/devcontainer.json` の設定に従って
Python 3.12環境が構築され、`requirements.txt` が自動でインストールされます。
ポート8000がフォワードされるため、起動後はブラウザからそのままアクセスできます。

## 文書生成MVP

setupで確認済みの個人情報・採用済み管理策から、標準テンプレート
（`app/document_templates.py`）に事実データを当てはめて文書（`app/documents.py`）を
組み立てます。AIによる自由作文は行いません。今回生成する文書は次の5種類です。

* 個人情報管理台帳：confirmedな個人情報から一覧を生成（管理策の採用有無は問わない）
* 個人情報保護教育手順：`education` 管理策がadoptedの場合のみ生成
* 委託先管理手順：`vendor_management` 管理策がadoptedの場合のみ生成
* アクセス権限管理手順：`access_control` 管理策がadoptedの場合のみ生成
* 紙媒体管理手順：`paper_management` 管理策がadoptedの場合のみ生成

各文書は `draft`（下書き・情報不足）／`ready`（準備完了）／`not_applicable`
（管理策未採用のため生成対象外）のいずれかの状態を持ち、不足している情報は
文書プレビュー画面に明示されます。文書はリクエストのたびに元データから組み立て
直すため、setupや教育・委託先管理の画面でデータを変更すると、次に文書を開いた
ときに内容が更新されます（文書のスナップショット保存・版管理は未対応）。

## アクセス権限管理・紙媒体管理MVP

RISK-001（不正アクセス）・RISK-002（紙媒体の紛失・盗難）が確認済み（confirmed）に
なると、setupの管理策候補として「アクセス権限管理」「紙媒体の保管・持出し・廃棄管理」が
提示されます（`app/risk.py` の `recommend_controls_from_confirmed_risks()`）。
提示・確認・採用の流れは既存の教育管理・委託先管理と同じで、採用可否の正本は
引き続きsetup側の `ControlSuggestion.status` のみです。

* アクセス権限管理（`/access-control`）：対象アカウントのアカウント確認・不要アカウント
  削除・権限レビュー・実施結果承認の状況を管理します（`ACC-001`〜`ACC-004`）。
* 紙媒体管理（`/paper`）：紙媒体の施錠管理・持出しルール・廃棄確認・実施結果承認の状況を
  管理します（`PAP-001`〜`PAP-004`）。

トップページでは、setupで採用（adopted）されていない管理策については「未採用」と表示し、
運用中であるかのような適合／要対応の表示はしません。

## 現在のMVP方針

教育管理・委託先管理・アクセス権限管理・紙媒体管理・初期設定（個人情報台帳・リスク・
管理策）・文書生成MVPを実装済みです。DB・認証・AI文章生成・文書の版管理・電子署名などは
今回も未導入です。

## 商品設計・価値提供の方向性（MVPレビュー観点）

MVPレビューでは、単に「機能が動くか」だけでなく、**中小企業のPマーク担当者にどのような価値を提供できるか**を同時に確認する。

### 基本的な価値提供

この製品は「Pマークを知っている人向けの管理ツール」だけを目指すのではなく、
**Pマークや個人情報保護実務に詳しくない担当者でも、必要な判断に近づき、次に何をすべきか分かるツール**を目指す。

担当者に台帳や文書を一から作らせるのではなく、会社・業務の実態について回答していくことで、
個人情報、リスク、管理策、台帳、文書、運用タスクが段階的に組み上がる体験を重視する。

### 入力負担を減らす設計原則

利用者入力は、原則として次の優先順位で設計する。

1. システムで自動判定できるものは自動判定する
2. すでに回答済みの情報は再利用する
3. システムが推奨値を提示し、利用者は確認・修正する
4. 選択肢から選べるものは選択式にする
5. 必要な場合のみ数値・短文入力を求める
6. 自由記述は最後の手段とし、使用する場合は入力例を表示する

例として、個人情報台帳の保管形態・保管場所・廃棄方法・保存期間等は、可能な限り標準選択肢や業務回答からの推奨値を利用し、同じ内容を個人情報ごとに何度も入力させない方向で設計する。

保存期間については、利用者が適切な期間を知らないことを前提とし、関連法令等に明確な保存期間がある場合はその根拠を踏まえた候補を提示し、明確な法定期間がない場合は利用目的・業務特性等に基づく標準案を提示して利用者が確認する方式を検討する。法令上の一律期間がないものを、法定期間であるかのように表示しない。

### PマークAI（将来の有料オプション候補）

ベース製品はAIがなくても、質問、候補提示、台帳、リスク、管理策、文書、運用タスクをルールベースで進められることを前提とする。

その上で、将来的な **PマークAI** は有料オプションとしての提供を検討する。

PマークAIの価値は、単なる一般的なチャット回答ではなく、システムに登録された以下の情報を前提に、担当者の判断負担を下げることに置く。

* 会社・業務の回答
* 確認済み個人情報
* リスク評価
* 採用済み／非適用の管理策と判断理由
* PMS文書・社内ルール
* 関連法令・Pマーク要求事項
* 現在の運用状況・不足事項

目指す役割は、担当者に代わって勝手に決定することではなく、
**「なぜこの選択肢なのか」「自社の場合はどう考えればよいか」を会社固有の状況に翻訳して説明し、担当者が判断しやすくすること**。

この将来拡張を可能にするため、現行MVPでも判断結果だけでなく、候補となった理由、関連する個人情報・リスク・管理策、非適用理由など、AIが将来根拠として利用できる構造化情報を可能な範囲で保持する。

### MVPレビュー時に確認する商品観点

今後のMVPレビューでは、機能テストに加えて少なくとも次を確認する。

* 担当者が「今何をすればよいか」を迷わないか
* 同じ内容を何度も入力させていないか
* 専門知識がなくても選択肢・推奨値・説明から判断できるか
* システムが自動化できる判断を利用者へ押し付けていないか
* 重要な判断について理由・根拠が分かるか
* ベース製品だけでも十分な価値が成立しているか
* 将来PマークAIを追加したとき、担当者の判断支援として自然に価値を上乗せできるか

### UXアイデア（未決定）

以下は現時点では実装決定ではなく、将来のUX候補として保持する。

* 項目名の `?` / `i` 等にマウスオーバーすると補足説明を表示する
* 入力項目を選択すると、画面右側や欄外に判断の目安・根拠・入力例を表示する
* 長い説明を常時表示せず、必要なときだけ展開できるヘルプを用意する
* 将来PマークAIへ「この項目は自社の場合どう考える？」とその場で質問できる導線を設ける

これらはMVPの利用レビューを通じて、情報量・入力負担・画面の分かりやすさとのバランスを見ながら判断する。
